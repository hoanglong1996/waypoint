run_pipeline data flow

Directed graph of EtlApplication.run_pipeline() in src/application/application.py. Nodes are the pipeline steps in execution order, arrows carry the data each step hands on. Hover a step to follow its inputs and outputs.

  • CallRail
  • Google Ads / Arena
  • Merge
  • Persist
  • data passed on (label = input name)
  • same list updated in place
  • count recorded to Redis
Fan-out / fan-in. instances feeds both read_campaigns and read_gads_clickview; merge_calls_clickview joins calls, campaigns and click views.
In-place steps. record_call_statistics and dealing_location_code modify the same call_statistics list (recording URL, location fields) before save_call_statistics posts it. dealing_location_code is not audited as a separate step.
Audit trail. Every step runs through StepAuditor.run(), which stores only item counts under callrail:audit:{env}:{run_id}:{NN}-{step} (30-day TTL). Redis problems never stop the run.
Failure. Any exception is printed and re-raised; main.py reports it to Sentry and exits non-zero.
