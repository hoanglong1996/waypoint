Waypoint system design

Waypoint answers one question about a nightly ETL run: did every step run, and did data survive each hop? Three parts cooperate: the waypoint-etl SDK inside the pipeline, Redis as the store, and Waypoint Monitor as the dashboard. They never talk to each other directly. The Redis key layout is the whole contract between them.

2. Key contract: who writes what

Key shape: waypoint:{pipeline}:{env}:{run_id}:{item}, where run_id is the UTC start time, YYYYMMDDTHHMMSSZ. Values are JSON with a version field v.

3. How a run moves through the system

Design rules worth knowing

  • Audit must never break the pipeline. Every SDK write is wrapped; failures are logged and swallowed. Without init, the decorator is a no-op.
  • Counts, not contents. Records hold identities, times and item counts. No business data reaches Redis.
  • Data loss is derived, not reported. The monitor flags a step whose output is 0 while an input was above 0.
  • Clocks must agree. beat_at comes from the pipeline host and is compared with the monitor's clock, within HEARTBEAT_DEAD_SECONDS.
  • Permissions mirror roles. Pipeline account: write waypoint:*. Monitor account: SCAN, MGET, PING, plus SET/PTTL on waypoint:*:died. With read-only access the monitor still works; Died verdicts just aren't kept across restarts.
  • Version safety. Records carry v; a dashboard that doesn't know a version shows "Unsupported record version" instead of wrong data.
